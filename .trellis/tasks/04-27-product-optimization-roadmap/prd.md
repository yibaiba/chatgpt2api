# brainstorm: 产品优化路线图

## Goal

为 ChatGPT2API 制定一份以产品体验为核心的优化路线图，明确近期最值得投入的产品方向、MVP 范围、验收标准与后续阶段拆分，避免继续以“功能堆叠”方式推进而忽略首次上手、日常运维和创作复用体验。

## What I already know

* 项目当前已经具备较完整的能力面：图片生成、图片编辑、多图编辑、号池管理、远端 CPA / Sub2API 同步、普通用户权限、代理池、自托管部署。
* 当前 Web 主要页面包括：`/login`、`/image`、`/accounts`、`/settings`，首页会根据登录态直接跳转到目标页。
* 登录页当前为单字段密钥登录，强调“输入密钥后进入对应页面”，但缺少首次使用引导和后续动作建议。
* 图片工作台已经具备较强的操作能力，但整体仍偏参数驱动与历史回看，场景模板、推荐动作与任务状态表达还有优化空间。
* 号池管理页当前更偏表格和工具页，适合熟手操作，但“系统健康度”“同步成效”“建议动作”还没有被产品化表达。
* 设置页承载了 CPA、Sub2API、代理池、普通用户、系统配置等多类能力，信息密度较高。
* README 对外传达的核心价值包含：图片能力、号池能力、远端自动同步、普通用户权限、自托管部署。

## Assumptions (temporary)

* 这次优先做的是“产品规划”，不是立刻全量实现。
* 本次规划希望落到一个可执行的 MVP 方向，而不是纯泛化建议。
* 第一阶段更适合聚焦一个主轴，避免同时推进 onboarding、运维看板、图片场景化三条大线。

## Open Questions

* 无阻塞问题。由于用户当前未在线确认，本次先按默认推荐路线收敛到“首次成功路径优先”，后续如需可再调整。

## Research Notes

### Current product shape

* **Entry flow**：首页会按登录态直接跳到 `/login` 或角色默认页，说明当前产品假设用户已经知道下一步要做什么。
* **Admin surface**：管理员核心操作散落在 `/accounts` 与 `/settings`，属于高能力密度、低引导型工具产品。
* **Creation surface**：`/image` 是普通用户和管理员共享的主工作台，已经是最接近“产品核心体验”的页面。

### Comparable product patterns

结合同类 AI 工具 / 运维工具常见模式，可归纳出三条可行优化主线：

**Approach A: 首次成功路径优先**（Recommended）

* How it works:
  * 管理员首次登录后不直接进入复杂页面，而是进入轻量 onboarding / setup checklist
  * 引导完成“账号源接入 → 可用状态确认 → 首次出图”
* Pros:
  * 最快降低新用户上手门槛
  * 能同时串起设置页、号池页、图片页
  * 对现有能力复用高，实现风险较低
* Cons:
  * 对老用户日常运维提效有限
  * 更偏转化与理解，不直接增强深度能力

**Approach B: 号池运维面板优先**

* How it works:
  * 把号池管理从表格操作页升级为健康面板 + 趋势 + 建议动作
  * 突出同步结果、异常率、可用配额、待处理问题
* Pros:
  * 最能强化项目差异化价值
  * 对管理员价值直接、明确
* Cons:
  * 普通用户几乎无感
  * 需要补较多聚合数据和状态口径

**Approach C: 图片工作台场景化优先**

* How it works:
  * 为图片页增加模板、预设场景、推荐动作、结果复用路径
  * 从“参数面板”升级为“创作工作台”
* Pros:
  * 最容易提升日常使用频率和感知价值
  * 对普通用户和管理员都直观
* Cons:
  * 若首次接入与号池状态仍然复杂，价值会被前置门槛抵消

## Expansion Sweep

### Future evolution

* 后续可形成双端分层：管理员运维端 + 普通用户创作端
* 若未来扩展更多模型或工作流，统一 onboarding / 健康状态 / 模板体系会更容易承接

### Related scenarios

* 登录后默认落点、设置页入口、号池状态和图片页任务反馈应保持一致的产品语言
* 普通用户权限体验应和管理员路径有明显区分，但不能断裂

### Failure & edge cases

* 首次接入失败时，要告诉用户“下一步怎么修”
* 远端同步失败、账号异常、额度不足、出图失败等应尽量可恢复、可解释

## Technical Approach

先完成产品路线图收敛，再根据确认的主轴拆成实现任务：

1. 先以“首次成功路径”作为 phase 1 主线
2. 将该主线拆成一个串联式管理端引导流，而不是做新的孤立页面
3. 在现有页面中加入必要的信息层和引导层：
   * 登录后的 setup checklist / first-run card
   * 账号来源连接状态与下一步动作
   * 可用账号 / 配额 / 最近同步的简明状态
   * 跳转到图片工作台并完成首次生成
4. 基于 MVP 再进入 Trellis implementation planning

## Decision (ADR-lite)

**Context**

当前项目同时存在三条值得投入的产品线：首次成功路径、号池运维面板、图片工作台场景化。若三条并行推进，范围会快速失控，且短期内最关键的问题——“第一次进来怎么成功用起来”——仍然无法解决。

**Decision**

第一阶段选择 **Approach A: 首次成功路径优先** 作为主轴。

**Consequences**

* 好处：
  * 能最快降低新用户理解门槛
  * 能串联现有管理员主流程
  * 复用当前页面和能力，落地风险较低
* 代价：
  * 号池运维效率和图片深度创作体验不会在第一阶段被充分提升
  * 后续仍需要单独推进运维面板与场景化创作两条线

## MVP Scope

### In Scope

* 管理员首次登录后的“下一步做什么”可见化
* 一个清晰的 setup checklist，覆盖：
  * 是否已配置账号来源
  * 是否已有可用账号
  * 是否已成功完成首次出图
* 关键系统状态卡片：
  * 可用账号数
  * 异常 / 限流账号摘要
  * 最近一次远端同步结果（如存在）
* 从 checklist 到相关页面的明确跳转动作
* 首次成功后的收尾状态（例如“系统已可用，可继续进入工作台创作”）

### Out of MVP

* 号池趋势图、异常原因细分图、运维看板
* 图片模板库、推荐 prompt、场景化工作流
* 设置页的全面重构
* 普通用户端的完整独立产品化改造

## Roadmap

### MVP

* 定义管理员首次成功路径
* 在登录后默认落点增加 setup / readiness 反馈
* 打通“连接来源 → 检查状态 → 首次出图”的串联路径

### Next

* 将号池页升级为轻量健康面板
* 增加最近同步结果、异常摘要和建议动作
* 优化首次成功后的回访体验，而不仅是首次进入

### Later

* 图片工作台模板化 / 场景化
* 管理员端与普通用户端双产品层次拆分
* 更完整的系统状态中心与失败恢复建议

## Implementation Plan (small PRs)

* PR1: 建立首次成功信息架构（登录后落点、setup checklist 容器、基础状态聚合）
* PR2: 打通 checklist 与设置/号池/图片工作台的操作链路
* PR3: 完成首次成功态、失败提示与文案收口
